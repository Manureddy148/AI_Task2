## The denominator question

A denominator is a claim about what you're holding constant while comparing. On
this corpus, for the *same content*:

* **per word** — Hindi packs less content per word than English (25.3 vs 21.6
  words/sent), Dravidian packs more (≈16 words/sent, agglutination), Bengali and
  Marathi sit in between. So tok/word *understates* Hindi's premium by 15% and
  *overstates* Kannada's by 36% (gpt2: per-word says 6.34× / 18.48×; the
  content-constant truth is 7.42× / 13.59×). A metric whose per-language error
  runs −15%..+36% cannot set per-language budgets.
* **per grapheme / per code point** — script-dependent unit ("char" ≠ "char"
  across scripts; matras merge into clusters; `len()` counts neither
  consistently). gpt2 hin looks 11.4× worse per grapheme, ~7.5× per code point
  (7.46 on the pipeline's NFC text, asserted by `verify.py`) — two more
  arbitrary answers from the same tokens.
* **per UTF-8 byte** — encoding artifact: Indic scripts spend 3 bytes/code point,
  English 1. It *flatters* Indic: gpt2 hin drops to 2.9×, and under xlm-r or
  MuRIL every Indic language shows a *lower* tok/byte than English (e.g. MuRIL
  tam 0.069 vs eng 0.209 — "Tamil is 3× cheaper"), which is false for cost: the
  same content still needs 1.06× the tokens. A denominator that can flip the
  sign of the conclusion is disqualified.
* **per parallel sentence** — holds the content itself constant. This is the only
  denominator whose ratio *is* the quantity leadership pays for: relative
  tokens-per-request for equivalent traffic.

## The single number that should drive routing and cost

> **Token parity vs English on parallel text, measured with the tokenizer of the
> model you would actually serve** — for our current gpt2-tokenizer stack:
> **hin 7.42× [7.34, 7.51], kan 13.59×, tam 15.54×, tel 12.97×, ben 9.61×,
> mar 7.86×**.

Why this one: (1) its denominator (content) is the unit revenue and cost actually
scale with; (2) it is a *within-tokenizer* ratio, so it's well-defined even
though token counts aren't comparable across tokenizers; (3) it maps directly
onto the decisions on the table — *serve as-is* (budget the premiums above) or
*route to an Indic-aware target* (premiums become 1.0-1.2×, MuRIL row,
re-measured with the actual target's tokenizer before committing).

Three honest footnotes. Absolute tok/sent across tokenizers is a capability
comparison, not a price list (per-token cost differs across model families; and
MuRIL is an encoder vocab — evidence of what Indic-focused vocabulary allocation
achieves, not a drop-in serving tokenizer). A multilingual vocabulary prices
English slightly higher: xlm-r +13.4%, MuRIL +2.0% vs gpt2 on the same English
sentences — routing is per-language, not fleet-wide. And parity on *romanized*
Indic text is a different, measured quantity (`../audit/romanization.py`): 2.25×
for chat-style Hindi on gpt2 — but on o200k romanization is *worse* than native
for Hindi/Marathi/Bengali (hin 1.87× vs 1.57×), a within-CI tie for Kannada, and
*cheaper* for Telugu; Tamil's romanized figure is scheme-inflated (honest range
2.37-3.09× on gpt2). Script mix belongs on the production dashboard.

Method notes: micro aggregation throughout (macro shown for contrast; <1%
difference on this corpus, see A2-B3); no lowercasing; NFC applied and measured
(≤ +0.11% tokens hin, +0.51% ben). The v0 method run unmodified on this corpus
reports hin 6.11×, kan 17.53×, tam 19.52×, tel 15.97× (see `../audit/repro_v0.md`)
— wrong by −18% (hin) to +29% (kan) against the content-constant truth, which is
the concrete damage the A2 flaws do on real data.
